# Crate map

<p class="kp-lede">Khora is built like a house of several floors. Each floor rests on the floors under it and never on one above, so the ground floor can be rebuilt without touching the roof's furniture, and a room upstairs can never pull the stairs out from under the others.</p>

Each floor here is a **crate**: a Rust package, compiled on its own, which
names the other crates it uses. This page is the lookup table: every crate,
what it holds, the tier it sits in, and where to find a given piece of code.
*Why* the engine is layered this way is the [CLAD](../concepts/clad.md) page.

## The crates

The workspace has **17 members**:

- 14 `khora-*` crates;
- `sandbox`, the example game (`examples/sandbox`);
- `xtask`, the build automation (`cargo xtask …`, `cargo gate`);
- `workspace-hack`, generated by `cargo-hakari`. It holds no code: it gives
  every third-party dependency one feature set, so `cargo t -p <crate>` and
  `cargo gate` build the same engine. Never edit it by hand; run
  `cargo hakari generate` after changing a dependency.

A fifteenth `khora-*` crate, `khora-macros`, is a **path crate**: a dependency
of `khora-data`, `khora-script` and `khora-lanes`, not a member.

| Crate | What it holds |
|---|---|
| `khora-core` | The contracts every other crate meets. The lane contract: `Lane`, `LaneFamily`, `LaneInputs` / `LaneOutputs`, `Level`, `Cost`, and its plumbing (`LaneBus`, `OutputDeck`, `HostViews`). The `Agent` trait, a family's registration (`register_agent!`), `Place`, `Layer`, `Wake`, `Activation`. The GORNA protocol types. The `Residency` trait. The backend traits (graphics, physics, audio, layout). Math, the `Runtime` containers, `EngineContext`, the scene format. Uses no crate of the workspace. |
| `khora-macros` | `#[derive(Component)]`, `#[derive(LaneInputs)]` / `#[derive(LaneOutputs)]`, `#[ergon_fn]`. |
| `khora-data` | The data layer: CRPECS (`World`, storage, queries, change detection, AGDF layout), the components, the Flows and DataSystems, the residencies (`register_residency!`), the frame graph and `register_pass!`, persistence (`scene/`). |
| `khora-control` | The decision side: `DccService`, GORNA (rounds, the arbiter, the cost book), the frame governor, the `ExecutionScheduler` (lending, layers, waves, the worker pool), the Substrate dispatcher. |
| `khora-script` | **Ergon**, the gameplay language: lexer, parser, checker, bytecode, VM, field arena, resume and hot reload. Uses `khora-core` and `khora-macros` only, so the compiler and the VM are tested without booting an engine. |
| `khora-telemetry` | `TelemetryService`, metrics, monitors. |
| `khora-infra` | The default backends, one folder each: `graphics/wgpu` (and the `.wgsl` tree with its composition), `physics/rapier`, `physics/khora` (in-house, incomplete), `audio/cpal` with `DefaultMixBus`, `ui/taffy`, `ui/text`, `ui/egui`, `platform/winit`, `telemetry` (resource monitors), `memory`. Uses `khora-core` only. |
| `khora-tool-ui` | The tools' design system: the brand palette, shared widgets, the dock tree. Used by `khora-editor` and `khora-hub`; never reached by the SDK, so a game never compiles Khora's brand. |
| `khora-io` | Everything that crosses the disk: `AssetService`, decoders, the VFS, signed packs, the trust boundary (`trust/`), `SerializationService`, `SceneLoadHub`, the project script compiler, atomic and bounded file access (`fs/`). |
| `khora-lanes` | One folder per family (`audio`, `loading`, `physics`, `render`, `script`, `shadows`, `skybox`, `ui`, `overlay/{grid,wireframe,gizmo}`): its `LaneFamily`, its lanes, and its `registration.rs` holding the family's one `register_agent!`. |
| `khora-agents` | `LaneAgent` (`lane_agent/`), the one implementor of `Agent`, and the boot that builds one per registered family (`registered_agent.rs`). |
| `khora-sdk` | The only public API for games: `EngineApp`, `GameWorld`, `Vessel`, `run_winit` / `run_default`, `open_game_assets`, `prelude`. Mapped in [SDK surface](./sdk.md). |
| `khora-editor` | The editor, an app on the SDK. |
| `khora-hub` | The project launcher, an app on the SDK. |
| `khora-runtime` | The generic player binary, stamped with a game's packed assets. |
| `sandbox` | The example game. |
| `xtask` | Build automation and the workspace's layout checks. Uses no crate of the workspace, so `cargo gate` builds it before the engine. |
| `workspace-hack` | Generated; unifies third-party features (above). |

## The tiers

A crate may use the crates of the tiers below its own, and only the ones its
row names. Never a cycle.

| Tier | Crates | Uses |
|---|---|---|
| floor | `khora-core`, `khora-macros` | nothing |
| on the floor | `khora-data`, `khora-control`, `khora-script`, `khora-telemetry`, `khora-infra`, `khora-tool-ui` | core; data and script add macros; control adds data |
| middle | `khora-io` | core, data, script, telemetry |
| middle | `khora-lanes` | core, data, macros, script |
| strategists | `khora-agents` | core, data, lanes, script (`khora-infra` as a dev-dependency only, for its tests) |
| façade | `khora-sdk` | agents, control, core, data, infra, io, lanes, telemetry |
| apps | `khora-editor`, `khora-hub`, `khora-runtime`, `sandbox` | sdk; the editor and the hub add tool-ui |

<li><strong>The floor.</strong> <code>khora-core</code> holds the contracts, <code>khora-macros</code> the derives. Neither uses another crate of the workspace.</li>
<li><strong>On the floor.</strong> Six crates stand on <code>khora-core</code>. <code>khora-control</code> also uses <code>khora-data</code>; <code>khora-data</code> and <code>khora-script</code> use the macros. <code>khora-infra</code> is here, not on top: it implements the core's backend traits and needs nothing else.</li>
<li><strong>The middle.</strong> <code>khora-io</code> uses data, script and telemetry; <code>khora-lanes</code> uses data, script and the macros (the lane derives). Lanes never reach <code>khora-infra</code>: they meet the backends through the core's traits.</li>
<li><strong>The strategists.</strong> <code>khora-agents</code> uses lanes, data and script. It never uses <code>khora-infra</code>: an agent only chooses, and its lanes reach the backends through the <code>Runtime</code>.</li>
<li><strong>The façade.</strong> <code>khora-sdk</code> gathers the engine for a game: agents, lanes, io, control, data, infra, telemetry, and core.</li>
<li><strong>The apps.</strong> The editor, the hub, the player and the sandbox use the SDK only; the editor and the hub add the tools' design system, <code>khora-tool-ui</code>.</li>
</ol>
</figure>

Two edges are easy to get backwards. **`khora-agents` never uses
`khora-infra`**: an agent reaches no backend, its lanes go through the core's
traits in the `Runtime`. And **`khora-infra` uses `khora-core` only**: it is a
floor tenant beside `khora-data`, not the top of the stack.

The manifests are checked by `xtask/tests/crate_graph.rs`: every crate stays
inside the crates its tier allows (`every_crate_stays_in_its_clad_tier`),
`khora-core` and `xtask` use no workspace crate, `khora-infra` and
`khora-tool-ui` use `khora-core` only, the SDK never reaches `khora-tool-ui`,
and `khora-lanes` never reaches `khora-infra`. Dev-dependencies are left out:
a test may reach any crate. A new crate gets a row in `RULES.md` §3 and in that
test's `CLAD_TIERS` before it builds.

Abstract traits live in `khora-core`; each concrete backend lives in its own
folder under `khora-infra`. Changing a `khora-core` trait means updating every
implementation in the same change.

## Where things live

| Concern | Crate / module |
|---|---|
| Lane contract and plumbing | `khora_core::lane` (`contract/`, `plumbing/`) |
| Agent trait, registration, places and layers | `khora_core::agent` |
| GORNA protocol types | `khora_core::agent::gorna` |
| Residency trait | `khora_core::residency` |
| Math types | `khora_core::math` |
| Runtime containers (`Services` / `Backends` / `Resources`) | `khora_core::runtime` |
| Scene file format and `SerializationGoal` | `khora_core::scene` |
| ECS world, storage, queries, components | `khora_data::ecs` |
| Flows (read-only projectors) | `khora_data::flow` (`register_flow!`) |
| DataSystems (transform propagation, ECS upkeep) | `khora_data::ecs::systems` |
| Residencies (meshes, images, materials on the GPU) | `khora_data::residency` (`register_residency!`) |
| Frame graph and pass slots | `khora_data::render` (`register_pass!`) |
| Scene records, encodings, saves, prefabs | `khora_data::scene` |
| DCC, GORNA rounds, the arbiter, the governor | `khora_control` (`dcc_service/`, `gorna/`, `governor/`) |
| Scheduler and worker pool | `khora_control::scheduler`, `khora_control::worker_pool` |
| Families and their lanes | `khora_lanes::<family>` (`render`, `shadows`, `physics`, `audio`, `ui`, `script`, `loading`, `skybox`, `overlay`) |
| `LaneAgent` and the boot of the families | `khora_agents` |
| Ergon language (lexer, parser, checker, bytecode, VM) | `khora_script` |
| Script ↔ engine values | `khora_script::bridge`, `khora_core::script` |
| Asset index and asset loading | `khora_io::asset` (`AssetIndex`, `AssetService`) |
| Asset decoders | `khora_io::asset::decoders`: services, not lanes, since a decoder has no per-frame strategy to negotiate |
| Trust boundary and signed packs | `khora_io::trust`, `khora_io::asset` |
| Serialization service and scene loads | `khora_io::serialization`, `khora_io::scene_loads` |
| WGSL shaders and their composition | `khora_infra::graphics::shader` (the `.wgsl` tree), composed by `khora_infra::graphics::wgpu::WgpuPipelineSystem` |
| wgpu, Rapier, in-house physics, CPAL, Taffy, winit backends | `khora_infra::graphics::wgpu`, `physics::rapier`, `physics::khora`, `audio::cpal`, `ui::taffy`, `platform::winit` |
| Resource monitors | `khora_infra::telemetry` |
| The game's API | `khora_sdk` |
| Editor | `khora-editor` |
| Sandbox | `examples/sandbox` |
